## Key design decisions (and why)

1. **Header/detail split** (`sales_orders` / `sales_order_items`). An order has many products; storing one row per product avoids repeating order data and gives clean product-level analysis.
2. **Price and cost snapshots on order lines.** `unit_price` and `unit_cost` are copied into `sales_order_items` at sale time. Later product price changes must not rewrite history, and profit needs the cost at that moment.
3. **Inventory = current state + ledger.** `inventory` stores stock now; `inventory_transactions` records every movement. The two must reconcile, and a data-quality query checks this.
4. **Junction table for promotions.** One promotion covers many products and a product can be in many promotions, so `product_promotions` has a composite primary key.
5. **Identity surrogate keys.** `GENERATED BY DEFAULT AS IDENTITY` (the modern replacement for `SERIAL`) allows explicit IDs during bulk load.
6. **Money is `NUMERIC(12,2)`, never `FLOAT`,** to avoid rounding drift.
7. **Constraints split into two kinds.**
   - *Blocked by the database*: negative prices, quantity ≤ 0, invalid status values, promo end before start, reserved stock greater than on-hand.
   - *Allowed on purpose* (detected by queries): duplicate-like customers (no UNIQUE on e-mail), malformed e-mail/phone, NULL category/supplier, case-variant category names.
8. **`updated_at` maintained by a trigger** (`set_updated_at()`), not by application code.
9. **Secondary indexes are kept out of `schema.sql`** so `EXPLAIN ANALYZE` can show before and after (see `indexes.sql`, Phase 8).
10. **Order status is `COMPLETED` or `CANCELLED` only.** Returns are separate records in `returns`, so return analysis uses the actual return data rather than a status flag that could disagree with it.

## Constraint summary

- **Primary keys:** every table. Junction table `product_promotions` uses a composite key.
- **UNIQUE:** sku, order_number, po_number, promo_code, store_code, category_name, segment_name, (order_id, product_id), (store_id, product_id), (purchase_id, product_id), (return_id, order_item_id).
- **CHECK:** 40+ (see `schema.sql`); each is exercised by `tests/test_schema_constraints.py`.
